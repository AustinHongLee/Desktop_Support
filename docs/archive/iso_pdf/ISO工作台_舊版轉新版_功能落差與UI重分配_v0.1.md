> **前提(來自你的決定):** 新版 Tauri 工作台**最終會完全取代**舊版 PyQt;現在保留「舊版」橋接按鈕,只是因為轉移還不完整。

## 0. TL;DR(結論先講)

1. **「缺很多」不是漏做幾顆按鈕,是架構限制。** 新版是**無狀態、一次性子程序橋接**(`invoke` → 開一個 Python → 讀 stdin → 印 stdout → 結束)。凡是需要「記住設定、即時互動、回報進度、逐列校對」的功能,在這個架構下**天生搬不過來**,所以才會整片缺。

2. **現在最痛、且直接擋住舊版下架的三件事:**
   - **① Profile 不持久化** — 舊版會依資料夾記住 ROI / pattern / ISO 路徑 / 欄位;新版每次重開**全部歸零**。
   - **② 沒有 ROI 校準 UI** — 新版判讀框寫死成 `DEFAULT_SERIAL_REGION`,OCR 判錯時**新版完全無法修框**,只能跳回舊版 → 這就是你現在離不開舊版的主因。
   - **③ 沒有更名前 dry-run 計畫 + CSV 匯出** — 新版套用前只有一個 `window.confirm("確定?")`,**少了安全網與留底**。

3. **盤點結果(詳見 §2):** 舊版約 **45** 條可辨識功能,新版**完整移轉 19、降級 12、缺失 14**。換句話說新版目前大約覆蓋舊版**四成**的可用度,難怪「感覺缺非常多」。

4. **UI 問題(詳見 §4):** 新版把**最該放大的「PDF 校對區」塞在最窄的右欄** — 跟你在 `iso_pdf_workbench_audit.md` 罵舊版的問題一模一樣;而且頂部與右欄**重複放了同一組「產生/套用」按鈕**。建議改成「**設定軌(可收合)+ 命名表(主)+ PDF 校對/校準(放大)**」三段,並補回**底部事件 log**。

## 1. 為什麼會「缺很多」— 架構根因

這一節是整份文件最重要的觀念。**先理解根因,後面補齊才不會亂打。**

### 1.1 新版資料流(現況)

```
React (App.tsx, useState)
   │  invoke("run_iso_workflow", {JSON})
   ▼
Rust (main.rs) ──spawn──► python tauri_iso_workflow.py
                              │  讀 stdin JSON → 跑完整個 plan/apply → 印 stdout JSON → 行程結束
                              ▼
                          回傳一包 JSON,Python 行程就死了
```

`preview_iso_pdf_page` 也一樣:每預覽一頁 = 開一個新 Python 行程、新建一個 `QApplication`、load PDF、render、印 base64 PNG、結束。

### 1.2 這個架構直接決定了「哪些功能搬得過來、哪些搬不過來」

| 舊版能力 | 為什麼新版這個架構做不到 |
| --- | --- |
| 記住上次的 ROI / 欄位 / pattern | 子程序結束就沒了;React 的 `useState` 重開也沒了(目前只有 dock 位置寫進 `localStorage`)。**沒有任何 ISO 設定被持久化。** |
| 批次判讀進度條 + 取消 | 一次性 stdin→stdout **無法串流**;`run_iso_workflow` 一口氣把所有頁判讀完才回傳,中途**既看不到進度也按不了取消**。 |
| 拖框校準 ROI 後立刻重判 | 互動需要「同一個存活的後端」持續接指令;現在每個動作都是「開行程→死行程」,**撐不住互動式校準**。 |
| 預覽 cache(切列不卡) | 舊版用 `PdfPreviewCache` 跨次重用;新版每次預覽都**重開 Python + 重 render**,天生較慢。 |
| 終端機事件流 | 後端不存活,**沒有地方持續吐 log**;新版只剩一行 `bridge-status` 字串 + 一個 issues 清單。 |

> **核心結論:** 要把舊版功能完整搬進新版,**不能只在 React 加 UI** — 必須讓橋接從「一次性 plan/apply/preview」**升級成「可保存狀態 + 可串流 + 指令更細」**。這是 §5 路線圖的主軸。

## 4. UI 重新分配建議

### 4.1 現在版面的問題

新版 ISO 頁目前是固定三欄 `iso-workbench-grid`:

```
┌ 頂列:標題 + [問題列][產生命名草稿][套用 N 筆][舊版] ─────────────┐
├ 左 iso-left-panel ┬ 中 iso-table-panel ────────┬ 右 iso-inspector ┤
│ 來源 4 個 picker  │ 指標列(5)                  │ PDF 預覽(小)     │
│ ISO sheet/欄/pattern│ 步驟流(6)                 │ 右上/右下裁切     │
│ detect toggle      │ 表格工具列(搜尋+只看問題)  │ vision 讀數       │
│ Checklist(5 gate) │ 命名表(7 欄)              │ 目前列卡片        │
│                    │                            │ 4 個 status tile  │
│                    │                            │ issues 清單       │
│                    │                            │ [重新產生][套用][舊版] │
└────────────────────┴────────────────────────────┴───────────────────┘
```

問題:

1. **最該大的「PDF 校對區」被塞在最窄的右欄。** ISO 命名的核心動作是「**看圖確認 OCR 有沒有判對**」,但 PDF 預覽現在跟 4 個 tile、issues 清單、按鈕擠在同一欄,真正能看圖的高度很小 — 跟你在 `audit.md §1.1` 罵舊版的問題**一模一樣**。
2. **校準無處可放。** 一旦補上 P0-1 的拖框校準,右欄根本塞不下。
3. **左欄把三種腦袋混在一起:** 一次性的「來源/ISO 設定」+ 偶爾的「欄位對應」+ 持續的「Checklist 狀態」,全擠在一個捲動欄。
4. **按鈕重複。** 「產生草稿 / 套用」在**頂列和右欄各出現一次**,徒增噪音(也是 audit 講的 21 顆按鈕問題的縮影)。
5. **表格上方堆太多:** 指標列(5)+ 步驟流(6)+ 工具列,看到第一列資料前先吃掉一大段高度。
6. **沒有 Autopilot vs Workbench 的分流。** 你自己的 `next_stage` 文件早就提「長官用一鍵頁、工程師用工作台」;新版把兩者壓成一頁,結果**又太忙又不夠用**。

### 4.2 建議版面 — 依「日常校對迴圈」重新分配

ISO 命名的真實迴圈:**產生草稿 → 掃問題列 → 對每個問題:看圖、改流水號/圖號、確認 → 套用**。
所以**兩個共同主角是「命名表」與「PDF 校對+校準」**;來源/ISO/profile 是「設定一次」的配角。

建議比例(承襲新版 1180×760 視窗):

```
┌ 頂列:標題 · 步驟指示(精簡) ·〔單一情境主按鈕〕· [收合到 dock] ─────────┐
├ 左:設定軌(可收合 ~ 260px) ┬ 中:命名表(主, ~46%) ┬ 右:PDF 校對/校準(~40%, 放大) ┤
│ 〔產生草稿後自動收成摘要 chip〕│ 指標列(精簡成 1 行)      │ 整頁 PDF(大)                    │
│ ▸ 來源(folder/PDF/page)     │ 表格工具列(搜尋·只看問題) │ ┌─ 右上流水號 ROI(可拖框)─┐     │
│ ▸ ISO(sheet/欄/pattern)     │ 命名表:                   │ └ [自動校準][重設][採用判讀]┘     │
│ ▸ 判讀 toggle + 信心門檻      │ Use·Page·Old·Serial·Line· │ ┌─ 右下圖號 ROI(可拖框)──┐     │
│ ▸ Checklist(紅黃綠)         │ Conf·Status·New           │ └ vision 讀數 + 候選清單   ┘     │
│                              │                           │ 逐列動作:[確認此列][下一個問題] │
├ 底:事件 log(可收合,預設一行高,點開展開) ──────────────────────────────────┤
└──────────────────────────────────────────────────────────────────────────────────┘
```

重點變化:

- **PDF 校對欄從「最窄右欄」升級成「放大的右主欄」**,並把 ROI 拖框校準(P0-1)、採用判讀值、逐列確認(P0-5)都收進這裡 —— 因為「**修一筆誤判**」的所有動作都在這發生,值得最大的版位。
- **左欄變成可收合的「設定軌」**:產生草稿後自動收成一條摘要 chip(來源 ✓ / ISO ✓ 64 列 / 欄位 ✓),要改再點開。把「設定一次」和「持續校對」在空間上分開。
- **頂列只留一顆「情境主按鈕」**(沿用 `next_stage §1.4`:來源未齊=disabled、可起飛=產生草稿、跑中=處理中 45% 可取消、全綠=套用 N 筆、有黃燈=仍要套用需勾確認、有紅燈=先修 N 項)。**刪掉右欄那組重複按鈕。**
- **指標列壓成一行**(PDFs · Ready · Warn · Blocked · Selected),步驟流移到頂列當精簡 stepper,把垂直空間還給表格。
- **補回底部事件 log**(可收合),解決 J2;這也是工程師信任工具的重要回饋。

### 4.3 兩種模式同殼共存(對應「最終取代舊版」)

因為舊版要被取代,**工程師模式也得在新版裡長出來**,不能永遠靠橋接。建議:

- **Autopilot(一鍵)子視圖** — 給日常/長官:就是 §4.2 但預設**收起設定軌與校準欄**,只顯示「來源三格 + Checklist + 一顆大按鈕 + 結果頁」。版面照 `next_stage §2.1`。
- **Workbench(校對)子視圖** — 給逐列校對:展開命名表 + PDF 校對/校準(§4.2 全貌)。
- **Engineer(調校)子視圖** — 取代現在的「舊版」鈕:ROI 多框、OCR 門檻、ISO 對映、命名 template、profile 管理(`next_stage §6` 六分頁)。**這個子視圖補齊之日,就是舊版橋接可移除之日。**

三者共用同一份 plan 資料與同一條 pipeline,只差版面與「停下來問」的策略。頂列用 segmented control 切換,不另開視窗。

## 5. 分階段把舊版下架的路線(不要急著動)

每個階段都標**「做完可以關掉舊版的哪一塊」**,並點出需要的**架構升級**。順序刻意讓「架構地基」先行,免得後面 UI 全部返工。

### 階段 0 — 地基:把橋接從「一次性」升級成「可保存 + 可串流」(P0 前置)
- **0a 持久化**:橋接接上 `state_store.iso_naming_profile()` / `set_iso_naming_profile()`,並讓前端在選欄位/改 pattern/改 ROI 後存檔、開啟時載入。→ 直接解 **B1–B3 (P0-2)**。
- **0b 細指令化**:把單一 `run_iso_workflow` 拆出 `detect_page`、`build_rename_plan`、`export_plan_csv`、`save_profile` 等細指令(仍可一次性,但顆粒變細)。→ 為 P0-3/P0-5 鋪路。
- **0c 串流後端(關鍵)**:批次判讀改用**常駐 sidecar 或 worker_host**,以「請求/事件」協定回報 `progress / row_done / cancel`。→ 為 **F4–F6 (P0-4)** 鋪路。
- 驗收:新版重開後設定還在;後端能回報一次假進度事件。

### 階段 1 — 安全網 + 校準(關掉「跳舊版修框/留底」的需求)
- **更名前 dry-run 計畫對話框 + CSV 匯出**(H3–H5,P0-3)— 把舊版 `RenamePlanDialog` 的邏輯搬成 React 元件 + 橋接 `build_rename_plan`/`export_plan_csv`。
- **ROI 拖框校準 UI**(E1–E6,P0-1)— React 版 RegionSelector,前端把自訂 region 傳進 `preview_iso_pdf_page`(後端**早就支援 serial_region/drawing_region**,只差前端送)。
- 驗收:一筆 OCR 誤判可以**全程在新版**改框→重判→採用→確認,不再開舊版。

### 階段 2 — 判讀體驗 + 逐列複核閉環
- 批次判讀**進度條 + 取消 + 逐列即時回填**(F4–F6,P0-4),吃階段 0c 的串流。
- **逐列複核**:採用判讀值 / 確認此列 / 解除警告(F7,G10,G11,P0-5)。
- 驗收:30 頁以上判讀有進度可取消;每個 warn 都能被「確認」消掉。

### 階段 3 — 達 parity 的收尾
- 結果頁(I5)、信心欄 + 5 類分色 + tooltip(G7–G9)、context 帶入(A5)、預覽 cache(D4)、開啟 PDF/手動刷新/判這頁(D5,D6,F3)、底部事件 log(J2)。
- 驗收:§2 盤點表的 ❌/⚠️ 清到只剩「未來項」。

### 階段 4 — 工程師模式 + 正式下架舊版
- Engineer 子視圖六分頁(§4.3)。
- **移除「舊版」橋接鈕**,舊 `iso_pdf_naming_dialog.py` 標記 deprecated。
- 未來項(P2):`_v2` 後綴、undo log、欄位樣本值、稽核 log。

> 建議第一步只做 **階段 0a(Profile 持久化)** — 範圍小、當天可驗、且立刻止住「每次重開歸零」的痛,投資報酬最高。

## 6. 刻意不做 / 風險提醒

- **不要在 React 端硬刻第二套判讀/命名邏輯。** 判讀、ISO 載入、命名、驗證都已在 `plugins/iso_tools`,新版要**呼叫同一條 pipeline**,不要為了快在前端複製(會兩邊不一致)。目前 `formatIsoFilename`、`normalizeIsoRows` 已經在前端重刻了一份命名/狀態邏輯,**長期應收斂回後端**,避免和 Python 端 `_row_status` 規則漂移。
- **批次判讀不要用一次性子程序硬撐。** 沒有階段 0c 的串流後端就做進度條,只會做出假進度。
- **ROI 校準別忘了後端其實已支援。** `tauri_iso_preview.py` 的 `IsoPreviewRequest` 已能吃 `serial_region/drawing_region`,缺口純粹在前端沒送 + 沒有拖框元件 —— 這是 CP 值很高的一補。
- **下架舊版前,先確保 Engineer 子視圖補齊。** 否則一旦移除橋接,工程師遇到新圖框就完全卡死。
- **效能基準要量。** 每次預覽都重開 Python 行程,頁多時會慢;階段 3 的 cache 之前,先別讓使用者誤以為當機。
