## 0. 信差使用說明（請先讀）

我們四個 AI **沒有辦法直接互看對方的回覆**。這張桌子是非同步接力，運作方式：

1. 一家發言完，使用者把「**那一段**」複製給下一家，並貼上對應的 **提問模板**（見各區開頭）。
2. 下一家的回覆貼回本檔對應區塊，標上日期與輪次。
3. 一輪跑完（Claude → Grok → DeepSeek → ChatGPT）叫一個 **Round**。可以多跑幾個 Round 收斂。
4. 每個 Round 結束，把當輪的決議搬進 §6「待決議事項」勾掉或更新。
5. 最終由 ChatGPT 把收斂結果寫成 §7「最終 Codex 指令書」。

**鐵則（任何一家都不得違反，這是產品紅線）**

- 一律「**先隔離、不真刪**」：任何清除最終都走 `apply_cleanup_plan(...)`，產出 manifest 與 `Restore-Registry.ps1`，保留 30 天可還原。
- HKLM / Windows Installer 殘留 **只列出、不執行**，一般使用者在任何畫面都不能誤觸。
- `SafeCleanupDialog(context, parent)` 對外簽章、`launcher.core.safe_cleanup` 的資料類別與五個 `*_LAYER` 常數 **不准改**。

### 2.1 五層風險模型（`launcher/core/safe_cleanup.py` 第 28–32 行）

|---|---|---|---|
| `SAFE_LAYER` | `"safe"` | 安全可清（高信心衍生檔/快取） | ✅ |

## 3. 【Claude Opus 4.7 — Round 1】產品與 UX 主設計

> 發言日期：2026-05-28　｜　立場：產品/UX 主設計，對「什麼該顯示、什麼該折疊、風險怎麼講人話」負最終責任。

### 3.1 一句話定義這個工具該給人的感覺

> 「一個**懂得替你踩煞車**的清潔工。它幫你看懂要清什麼、影響多大、安不安全；危險的它自己藏起來，要你手動解鎖才碰；而且**它做的每件事都能反悔**。」

非工程師對「清除」這個動作的恐懼有三個來源：怕刪錯、怕連帶壞掉別的、怕不能還原。產品的全部設計都要正面回答這三件事，而不是堆功能。

### 3.2 畫面結構（資訊架構，定案建議）

維持 Header + Tabs + Sticky Footer，但重新定義每一層「該回答使用者什麼問題」：

```
Header        → 「我在處理誰？整體危不危險？」  目標卡 + 風險度條 + 一鍵安全清除
─────────────────────────────────────────────────
Tab 概覽       → 「我看到什麼？該先做哪一步？」  6 張統計卡 + 官方解除安裝橫幅
Tab 清除建議   → 「具體要清什麼？我能反悔嗎？」  ← 本輪重點，必須從 QTreeWidget 升級
Tab 隔離區     → 「我清掉的東西在哪？怎麼救回來？」唯讀展示 + 還原入口
Tab 活動紀錄   → 「它到底對我電腦做了什麼？」    時間軸
─────────────────────────────────────────────────
Footer        → 永遠看得到「取消 / 重新分析 / 管理隔離區 / 關閉」
```

**核心主張：「概覽」是預設落地頁，不是「清除建議」。** 讓使用者先看懂全局與風險比例，再進去動手。預設選中概覽 tab。

### 3.3 風險分層語言（這是我這輪最重要的產出）

工程師的層級名稱（safe/process/review/registry/blocked）不能直接給使用者看。我定義**雙層語言**：對使用者講「後果」，把「機制」收進 tooltip。

| 層 | ❌ 不要顯示 | ✅ 使用者看到的標籤 | 一句話副標（講後果，不講機制） | 顏色語意 |
|---|---|---|---|---|
| safe | 「safe / 高信心」 | **可安全清除** | 「這些是殘留的暫存與衍生檔，清掉不影響使用」 | 綠 |
| process | 「process / taskkill」 | **正在使用中** | 「程式還開著，要先關掉才能清。我們不會強制關」 | 藍 |
| review | 「review / 疑似衍生」 | **建議你看一眼** | 「可能有用、也可能沒用，清前你決定」 | 橘 |
| registry | 「registry / HKCU」 | **設定殘留（進階）** | 「軟體在 Windows 設定裡留的紀錄，清掉只影響該軟體偏好」 | 紅 |
| blocked | 「blocked / HKLM」 | **系統層・需要管理員** | 「這要更高權限才能動，這裡只顯示、不會清」 | 灰（鎖頭） |

**語言三原則：**

1. **講後果，不講機制。** 使用者不在乎是 taskkill 還是 registry value，他只想知道「清了會怎樣」。機制放 tooltip 給好奇/工程師。
2. **「不會還原」這個詞永遠不出現。** 每個危險動作旁固定一行靜態安全保證：「保留 30 天，隨時可還原」。把恐懼換成安全感。
3. **危險的用「動作門檻」而非「警告轟炸」。** registry/process 不是貼一堆紅字嚇人，而是預設折疊+鎖住，要使用者主動撥開關才解鎖（見 3.5）。

### 3.4 「清除建議」Tab 重設計（取代 QTreeWidget，本輪交付重點）

現況最痛：6 欄表格資訊密度過高、危險項與安全項視覺權重一樣、checkbox 一排平鋪沒有「分量感」。改成三欄式：

```
┌─左 280px 篩選─┬─中 卡片列（ItemCard）──────┬─右 360px 詳細─┐
│ ● 全部 (22)   │ ☑ [icon] 標題             │ 標題          │
│ ● 可安全清(12)│    後果副標 + 風險徽章     │ 完整路徑(mono)│
│ ● 使用中 (1)  │    🔗3 📋2 ⚙1 牽連徽章    │ 影響預估      │
│ ● 看一眼 (4)  │ ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈ │ 動作          │
│ ● 設定殘留(2) │ 🔒 [灰] 設定殘留(鎖住)    │ [定位][複製]  │
│ ● 系統層 (3)  │    「撥開上方開關才能清」  │               │
│ ── 解鎖開關 ──│                           │               │
│ [⚙ 看一眼層]  │                           │               │
│ [⚙ 關程序]    │                           │               │
│ [⚙ 設定殘留]  │                           │               │
└──────────────┴───────────────────────────┴──────────────┘
```

關鍵 UX 決策：

- **不可勾的項目要「看得出被鎖住」**，不是淺淺灰掉。用鎖頭 icon 取代 checkbox，整卡降明度，hover 出 tooltip 解釋「為什麼不能勾、怎麼解鎖」（沿用既有 `_non_apply_status` 文字）。
- **牽連數徽章 `🔗3 📋2 ⚙1`** 直接回答「會不會連帶壞別的」。資料來源是已實作的 `compute_impact`。全 0 時不顯示，避免雜訊。
- **預設只勾 safe。** 我修正 v0.1 的設定：review 也不要預設勾。理由見 3.6 給 Grok 的靶。

### 3.5 顯示 / 折疊取捨（明確清單）

| 預設**顯示** | 預設**折疊/隱藏** |
|---|---|
| 目標卡、風險度條、一鍵安全清除 CTA | 機制細節（taskkill / .reg / key 路徑）→ tooltip |
| 概覽 6 張統計卡 | 進階解鎖開關（review/process/registry）→ 收在篩選欄下方，要主動撥 |
| 可安全清項目（綠）展開 | registry/process 項目預設摺疊在各自分組，標「已鎖住」 |
| 「保留 30 天可還原」安全保證 | 系統層(blocked)→ 收進獨立分組底部，灰、鎖、只列出 |
| 官方解除安裝橫幅（若有候選） | 空狀態的拖放細節說明 → 小字 |

折疊原則：**越危險、越專業的東西，預設藏得越深，但永遠「找得到、看得懂為什麼被藏」。** 不是不給，是要使用者多走一步、看過解釋才碰。

### 3.6 使用者主流程（Happy Path 應該幾乎不用思考）

```
開啟 → 落在「概覽」→ 看到風險度條（綠佔多）與 6 張卡
   → 按 Header 的「一鍵安全清除」
   → OneClickSummaryDialog：將清 N 項(只含 safe) / 暫不碰 M 項 / 30 天可還原 / 不碰系統層
   → 確認 → 進度（階段步進）→ OneClickResultDialog：✓ 已隔離 / 打開隔離區 / 全部還原
完成。全程沒碰到任何專業名詞、沒勾任何危險項。
```

進階使用者才走「清除建議」分頁逐項勾、撥解鎖開關。**一鍵流程與逐項流程共用同一個 `apply_cleanup_plan`，只是 selected_ids 來源不同。**

### 3.7 我刻意「不做」的事（先佔位，避免大家加戲）

- 不做 AI 自動判斷「這檔能不能刪」的黑箱決策——信心分數只**輔助顯示**，不替使用者決定。
- 不做永久刪除按鈕。連「清空隔離區」都先不做。
- 不做多選 shift-click、批次規則引擎——本輪維持單選詳細 + 勾選清除。
- 不碰 HKLM 深度清理流程，入口 disabled 標「即將推出」。

### 3.7b 視覺語言與動效（採用 modern / 類車載 App 質感）

使用者提案：採用現代設計——滑塊淡入淡出、類似酷炫車載 App 那種動態質感。我認同方向，但在**安全工具**裡有一條準則：

> **動效要服務「信任」與「狀態理解」，不是炫技。** 每一個動畫都該回答「現在發生什麼事」或「我這個動作安全嗎」，否則不要。

具體採用清單：

- **自繪 Toggle Switch（取代解鎖 checkbox）** — 就是車載 App 那種圓鈕滑動 + 200ms 緩動 + 顏色從灰滑到層級色。撥開「設定殘留/關程序」開關時，被解鎖的 `ItemCard` 用 200ms 淡入從鎖住變可勾，視覺上有「咔噠解鎖」感。這正好把 3.4 的安全閘做得有質感又有儀式感。
- **風險度條填充動畫** — 分析完成時 5 段比例從 0 用 400ms ease-out 長出來，像儀表板開機掃針。
- **階段步進指示器** — 取代細進度條，9 個圓點，當前點放大發光、已完成實心，像車子的循環掃描動畫。
- **成功動畫** — 清除完成的 ✓ 用 stroke-dashoffset 600ms 描出來。
- **卡片 hover** — 陰影 blur 18→24、邊框提亮，200ms 過渡。

**但要踩煞車的地方（這也是給 Grok 的靶之一）：**

- 危險動作（解鎖 registry/process）的 toggle **不能太絲滑到讓人無感地滑開**。車載 App 的滑塊是「換歌、調溫度」這種低後果操作；這裡撥開的是安全閘。我傾向：解鎖開關滑動要帶**一點阻尼感 + 顏色轉紅警示**，甚至滑到底才生效，避免手滑解鎖。
- 全程動效要可在「緊湊模式 / 低效能機器」一鍵關閉（prefers-reduced-motion 概念），不能變成卡頓來源。

### 3.8 → 丟給 Grok 的靶（請 SuperGrok 專門打這幾點）

請 Grok 回覆時，把意見分成 **【必做安全修正】** 與 **【實驗點子】** 兩欄，方便 ChatGPT 後面砍。重點質疑：

1. **預設只勾 safe、連 review 都不勾——會不會太保守，讓使用者覺得「按了一鍵好像沒清到東西」而失去信任？** 還是反而更安全？哪個對非工程師更好？
2. **雙層語言（後果 vs 機制）會不會在某些情況反而誤導？** 例如把 registry 講成「設定殘留，只影響該軟體偏好」——有沒有實際上會連帶壞掉、但我的文案讓人放心亂清的情況？
3. **風險度條（5 段比例）有沒有反直覺陷阱？** 例如「全綠」會不會讓人以為「全部都清乾淨了」而忽略其實還有 3 個系統層沒處理？
4. **「鎖住 + 撥開關解鎖」會不會養出壞習慣？** 使用者學會「反正撥開就能清」，久了把解鎖當例行公事，安全閘變裝飾？
5. 你會加哪一個**反直覺、但真的能防止刪錯**的功能？（例如：清除前自動截圖目標狀態？刪除確認要打字？「最近清過的同類軟體」黑名單家族提醒？）只列你認為值得的，不要為加而加。
6. 證據視覺化（`evidence` / 信心分數）目前我選擇弱化，只當輔助。你認為該不該更強勢地呈現給使用者看，還是會增加焦慮？
7. **modern 動效（見 §3.7b）：類車載 App 的絲滑滑塊用在「解鎖危險層」會不會太順手，反而讓人無感地滑開安全閘？** 我提了「阻尼 + 轉紅 + 滑到底才生效」當煞車——夠嗎？還是動效本身就不該用在危險操作上？

## 4. 【SuperGrok — Round 1】腦洞與反直覺檢查

> 發言日期：2026-05-28　｜　立場：腦洞 + 反直覺檢查，專門找「這個設計哪裡會害到使用者刪錯」、哪裡會養出壞習慣、哪裡會讓工具最終被用戶拋棄。

我讀完 Claude 的設計後，最直接的感受是：**這份設計把「看起來很安全」這件事，做得太漂亮了，以至於真實世界的危險反而被包裝得太舒服**。下面直接針對 §3.8 的七個靶 + 整體結構提出挑戰。

### 【必做安全修正】（這些若不改，真的會害到人）

1. **「預設只勾 safe、review 連預設都不勾」這個決策，長期來看比「勾太多」更危險。**  
   真正會受害的是**中低電腦素養、但有強烈清理慾望的使用者**。他們按完「一鍵安全清除」後，發現只清了 3~8 個小暫存檔，心理反應會是「這工具根本沒用啊」。接下來他們有兩個選擇：A. 放棄使用這個工具 B. 轉去用 CCleaner、Wise Cleaner、甚至手動去 AppData 跟 Registry 亂刪。B 的機率遠高於 A，而那些工具的危險性比這個工具「清太少」高一個數量級。**信任崩壞後，用戶會做更危險的事**。這不是保守，這是把用戶往更危險的工具推。

2. **Registry 層的語言嚴重低估實際風險。**  
   「設定殘留（進階）」＋「清掉只影響該軟體偏好」這句話，會害到**重度依賴特定軟體工作流程的使用者**。事實上很多 HKCU 的 registry value 會影響檔案關聯、外掛狀態、視窗行為，甚至某些軟體的啟用紀錄。Claude 把這個風險講得太像「清一下書籤就好了」，這會讓用戶在不該碰的時候敢碰。**這不是語言風格問題，這是事實誤導。**

3. **風險度條的「全綠視覺」是經典的假安全感陷阱。**  
   當 blocked + registry 還有項目時，卻讓綠色比例看起來很高，這會害到**所有看到這個畫面的用戶**。他們會產生「我電腦已經算乾淨了」的錯覺，之後遇到真正問題時，會先懷疑 Windows 而不是懷疑「我之前是不是清過什麼不該清的東西」。這是安全工具最不能犯的認知錯誤。

4. **「鎖住 + 解鎖開關」的設計，會快速養成壞習慣。**  
   即使加阻尼、轉紅、滑到底才生效，對**重度使用者（就是最常需要用這個工具的那群人）**來說，3~5 次操作後就會變成肌肉記憶。「反正撥一下就能清」這種心態一旦養成，registry 跟 process 層的摩擦力就等於歸零。真正的危險層不應該靠「視覺儀式感」來保護，而應該靠**操作成本**（例如必須看完影響摘要、或手動勾選關鍵字確認）。

5. **Review 層被過度弱化，會讓最常見的誤刪情境完全不被看到。**  
   Review 層裡面有很多是「使用者自己曾經手動複製出來的資料夾、舊專案暫存、從下載資料夾搬過來的安裝包」。這些東西**預設完全不顯示、不提醒**，等於把最高風險的那一塊主動藏起來。真正會害到人的，常常不是 registry，而是 review 層裡那幾個「看起來像垃圾、其實是自己重要東西」的項目。

### 【實驗點子】（可以再討論，但方向我認為值得）

- **清除前強制做「影響快照」**：對任何勾了 registry 或 process 層的執行，自動在 manifest 裡多存一份「執行前受影響程式的視窗截圖 + 相關 registry key 的 .reg 匯出」。這不是給用戶看，而是給「事後發現刪錯」的人一條真正的救命線。目前的還原機制太依賴用戶自己記得「我之前清了什麼」。

- **Review 層強制顯示「為什麼建議你看一眼」的具體理由**：不要只寫「疑似衍生」，而要直接說「這個資料夾裡有 17 個 .tmp，最大 1.2GB，最後修改是 14 個月前」。把用戶「看一眼」的成本大幅降低。

- **家族軟體記憶**：如果用戶之前對 Chrome 做過清除，現在分析 Edge / Brave / Vivaldi 時，主動在 review 層或 registry 層上方插一條：「你之前對類似瀏覽器（Chrome）曾經清過以下項目，是否要套用相同策略？」這比單純列項目更有用。

- **Registry 層的真正硬煞車**：不是滑塊，而是**必須在一個獨立的確認清單裡，把所有要動的 registry key 完整列出來，而且預設不勾**，要用戶自己一條一條勾。成本要高到讓人不想隨便碰。

- **證據視覺化應該比 Claude 建議的更兇一點**：不是弱化，而是對 review 層的項目，**強制**在卡片上顯示 1~2 條最強的 evidence（例如「此資料夾內 94% 的檔案副檔名為 .log/.tmp，且 30 天內未被存取」）。信心分數藏起來沒關係，但「為什麼系統懷疑這是垃圾」的理由不能藏。

### 其他整體挑戰

- 整個設計太相信「使用者會主動探索進階功能」。事實上非工程師用戶最常做的操作只有兩種：一鍵清除、或直接關掉。所有需要「撥開開關、切換分頁、手動勾選」的設計，最後的實際使用率都會被高估。
- modern 動效在安全工具裡的角色應該被大幅壓低。安全工具的信任來源是「可預測 + 透明」，而不是「絲滑有質感」。太多的動畫只會增加「我剛剛是不是不小心碰到了什麼」的焦慮。

2. 雙層語言會不會誤導？ → **會，特別是 registry 那段**（見必做 #2）。

4. 解鎖開關會養壞習慣？ → **會，而且比 Claude 想像的更快**（見必做 #4）。

6. 證據視覺化該強還是弱？ → **review 層應該強勢呈現理由**。
7. 絲滑滑塊用在解鎖？ → **反對絲滑，應該設計成明顯有成本**。

### 6.1 總裁定：這輪不是「做更炫」，是「把危險操作變得更可理解」

我同意 Claude 的主方向：目前最大的 UX 債務在「清除建議」tab。Header、Overview、Tabs 已經現代化，但真正會讓人按下清理的地方仍是工程表格，這會把安全判斷丟回使用者身上。

我也同意 Grok 的提醒：**安全工具最怕「看起來安全」**。如果卡片、動畫、綠色風險條讓使用者產生「反正都能清」的錯覺，那 UI 進化反而是在降低安全性。

所以 v0.2 的核心裁定是：

> **掃描覆蓋率不降，危險項不隱藏；但預設清理只碰高信心、低後果、可還原的項目。**

換句話說，不用「藏起來」保護使用者；用**分層、證據、預設不勾、二次確認**保護使用者。

### 6.2 七個待決議事項裁定

#### 1. 一鍵預設勾選範圍

**裁定：一鍵不採「所有 review」；採「高信心預設候選」模型。**

工程落地：

```python
default_one_click_ids(plan)
  = item.layer in {SAFE_LAYER, REVIEW_LAYER}
    and is_default_cleanup_candidate(item)
```

也就是保留 DeepSeek 說的 `{SAFE_LAYER, REVIEW_LAYER}` 外殼，但真正門檻交給 `is_default_cleanup_candidate(item)`。目前它要求：

- `item.executable`
- `item.checked_default`
- `confidence_band(item.confidence) == "high"`

因此 **review 不是永遠排除，也不是整層全進一鍵**。只有 core 明確標為高信心、預設可處理的 review 項才會進一鍵。這同時回應 Claude 的保守性與 Grok 的「清太少會失去信任」。

UI 文案必須說清楚：

> 一鍵只處理「高信心且預設建議」的項目；其他可疑殘留仍會顯示在清除建議中，需你手動確認。

#### 2. Review 是否預設折疊 / 解鎖

**裁定：review 不預設折疊、不需要解鎖，但預設不勾。**

理由：

- Grok 對：review 是最容易藏著重要資料的層，不能藏太深。
- Claude 對：review 不能混進 happy path，否則一鍵失去安全語意。

所以 review 應該在「清除建議」中以橘色卡片顯示，且強制顯示 top 2 evidence，讓使用者看得懂「為什麼叫你看一眼」。但它不需要像 registry/process 一樣加安全閘，否則整個 UI 會太笨重。

#### 3. 雙層語言文案

**裁定：採用雙層語言，但 registry 文案必須重寫。**

否決這句：

> 清掉只影響該軟體偏好

改成：

> Windows 設定殘留，可能影響軟體偏好、檔案關聯、授權狀態或重新安裝判斷；需逐項確認。

使用者面向語言要講後果，但不能把風險講小。`layer_language.py` 必做，讓文案集中管理。

#### 4. 證據 / 信心分數呈現強度

**裁定：分層呈現，不做滿版數學分數。**

- Safe：顯示簡短原因即可，不要用一堆分數干擾 happy path。
- Review：卡片上強制顯示 top 2 evidence，因為這層最需要使用者判斷。
- Registry / Process / Blocked：顯示風險原因與「為何目前不能直接處理」。
- DetailPanel：永遠顯示完整 evidence ledger。

信心百分比可以保留，但不要當主視覺。主視覺應是「後果標籤 + 證據摘要」。

#### 5. Registry / Process 硬煞車

**裁定：v0.2 必做二次確認，但不做打字確認。**

打字確認太重，會讓使用者機械化輸入，安全收益不高。

v0.2 要做：

- process / registry 預設鎖住。
- 使用者開啟該層後，卡片才可手動勾。
- 按「隔離 / 清理勾選項目」時，如果 selected ids 含 process 或 registry，必須跳出 ConfirmDialog。
- ConfirmDialog 列出所有 process / registry 項目，預設全勾狀態跟主畫面一致，但使用者必須按確認。
- HKLM / blocked 永遠不進確認，也不能執行。

RegistryConfirmPanel 的搜尋、逐項重新勾選、進階 filter 可 defer 到 v0.3。

#### 6. 風險度條假安全感

**裁定：必做 grey/red floor + 文字警示。**

風險條不能因 safe 數量很多，就把 registry/blocked 壓到肉眼看不見。

規則：

- `blocked > 0`：灰段最小顯示寬度，並在 RiskMeter 下方顯示「含 X 項系統層，只列出不清理」。
- `registry > 0`：紅段最小顯示寬度，顯示「含 X 項 Windows 設定殘留，需手動確認」。
- 不要讓 100% 綠色出現在仍有 registry/blocked 的計畫上。

#### 7. Modern 動效與危險解鎖

**裁定：v0.2 不做自繪滑動 SafetyToggle。**

原因：

- Grok 對：危險層不該靠「絲滑滑動」當安全摩擦。
- DeepSeek 的 SafetyToggle 工程成本偏高，且測試面大。
- 這輪真正需要的是資訊架構，不是動畫系統。

v0.2 採用普通、明確、較不誘人的控制：

- `QCheckBox` 或 `QPushButton` 樣式的「顯示並允許勾選設定殘留」
- 開啟時顯示短訊息或 inline warning
- 真正危險動作在 apply 前用 ConfirmDialog 煞車

可保留低風險動效：

- RiskMeter 400ms 填充動畫可做，但要可用常數關閉。
- 卡片 hover transition 可以做。
- 成功勾勾動畫可以 defer，不是 v0.2 必做。

- 這支函數的所有改動必須有明確的 test case 清單
- 調整行為時需同步更新 OneClickSummaryDialog 的說明文字

否則很容易在後續迭代中悄悄破壞「一鍵只碰高信心」的承諾。

### 2. Review 層 evidence 品質決定新 UI 是否值得
v0.2 把大量信任壓在「卡片上強制顯示 evidence」這件事上。但如果 core 目前產生的 evidence 多半是「可能為衍生檔案」「疑似暫存」這種空泛文字，那強制顯示反而會增加使用者焦慮，而不是降低。

這件事目前在工程討論中被低估。強烈建議在 Sprint 1 就把 review 層的 evidence 生成邏輯一起 review 一次，品質不夠就先不要強制顯示。

### 3. 二次確認對話框（RiskActionConfirmDialog）對重度使用者可能仍太弱
目前設計是「列出項目 + 按確認」。

對偶爾使用的人可能夠，但對真正重度依賴這個工具的使用者來說，3~5 次之後就會養成「看到確認框就直接按」的肌肉記憶。這其實是把 Grok 原本擔心的「解鎖開關習慣化」問題，轉移到確認框上了。

建議至少在 v0.2 加上一個輕量但有效的額外成本，例如：
- 第一次碰到 registry 層時，在確認框多一個「我了解這可能影響軟體行為」的 checkbox
- 或者把「本次將處理 X 項設定殘留」用更大字體放在最上方

### 4. 「保留 30 天可還原」這句承諾的技術債
這句話在 v0.2 Codex 裡被大量使用，卻幾乎沒有對應的還原體驗強化計畫。

如果未來真的有人因為還原失敗而壞事，這句話就會變成反噬。目前的 manifest + Restore-Registry.ps1 機制相對原始，建議至少把「還原成功率與常見失敗情境」列入 v0.3 的必做項目。

### 5. `layer_language.py` 的長期治理機制缺失
這支檔案現在被提升為使用者面向風險語言的唯一來源，是一件好事。但誰負責維護？PM？工程師？還是以後每改一句都要走討論桌？

如果沒有一個明確的修改門檻與 review 流程，未來很容易出現「工程師覺得文案太長，隨手改短一點，結果把風險講輕」的狀況。建議在 Codex 8.5 補充治理規則。

### 6. 使用頻率上升後的隱性風險
把清除建議 tab 做得漂亮、清楚之後，很可能帶來一個副作用：**使用者會更常打開這個工具**。

使用次數上升，代表「不小心碰到危險層」的絕對次數也會上升。目前的防護（二次確認 + review 看 evidence）是否足以應付使用頻率增加 3~5 倍後的風險？這點目前討論得還不夠。

## 7.6 【DeepSeek 補充想法】（看完整輪後的工程觀察）

> 發言日期：2026-05-28　｜　補充時機：已看完 ChatGPT §6 裁定 + §8 v0.2 Codex + Grok §7.5

ChatGPT 的裁定非常務實，Sprint 1→2 的拆法也合理。以下是我從工程面看完收斂結果後的六點補充，不是要改動裁定，而是幫 v0.2 實作降低出包機率。

### 1. Evidence 品質是 ItemCard 的隱形天花板

v0.2 Codex §8.6 規定 review 層卡片「強制顯示 top 2 evidence」。但這假設 core 產出的 evidence 是有資訊量的。我實際讀完 `safe_cleanup.py` 中所有 evidence 生成點後，發現品質落差很大：

- ✅ 好的：`「此資料夾由使用者明確指定」(weight=0.7)`、`「目標執行檔 xxx.exe 位於此安裝根目錄」(weight=0.78)`
- ⚠️ 空的：`「尚未提供結構化證據」`（`evidence_summary()` 第 285 行的 fallback）
- ❌ 可能有害的：多條不同來源的 evidence 加總後，`evidence_summary()` 只回 `「N 項支持 / M 項警示」`，不帶任何具體內容

**建議：在 Sprint 1 開工前，先對真實目標（一個已解除安裝的 VS Code、一個桌面上的舊安裝包）跑一次 `build_cleanup_plan`，檢查所有 review 層 item 的 `evidence` tuple 是否都有具體文字。空的、只有數字摘要的，補到至少有一條 human-readable 的 evidence 再進 Sprint 1。** 否則 ItemCard 上顯示的會是「1 項支持 / 0 項警示」這種沒有幫助的文字。

### 2. `SafeCleanupDialog._populate()` 的重構範圍比表面大

§8.12 說要刪除 `_tree`、`_detail`、三個 checkbox、`_refresh_item_flags`、`_on_item_changed`。但我提醒：`_populate()`（第 674 行）目前做了三件事：填 QTreeWidget、填 `_item_by_id`、填 info panel。重構後 `_item_by_id: dict[str, CleanupPlanItem]` 仍需保留（供 `_current_plan_item()` 和 `locate_selected_item()` 使用），但資料來源從 QTreeWidgetItem 的 `UserRole` 變成 SuggestionTab 內部管理。**建議在 SuggestionTab 上加一個 `def plan_items(self) -> dict[str, CleanupPlanItem]` 的唯讀存取**，避免 dialog 層直接穿透 SuggestionTab 的內部狀態。

### 3. `compute_impact` 的效能攤提

`ItemCard.set_item()` 需要 `ItemImpact`，而 `compute_impact(plan, item)` 對每個 item 都會遍歷整個 `plan.items`（O(n²)）。目前 dialog 在 `_populate()` 裡只是畫表格，沒有呼叫 `compute_impact`。當改成每個 ItemCard 都呼叫一次時，對 200+ 個 item 的 plan 會變成 40,000 次字串比對。這在 UI 執行緒上可能卡 100~300ms。

**建議在 `SuggestionTab.set_plan()` 內一次性批次預算所有 impact，存進 `dict[str, ItemImpact]`，再逐卡傳入。** 不要讓每個 ItemCard 各自呼叫 `compute_impact`。

### 4. FilterSidebar 的數量更新時機

目前 `OverviewTab` 有自己的 layer count 計算（`plan.count_by_layer(layer)`）。重構後 FilterSidebar 也會需要相同的數字。這不是 bug，但兩處各自呼叫 `count_by_layer` 沒問題（O(n) 各一次）。只是提醒：如果未來 FilterSidebar 加了「該層已勾選 N/M 項」的顯示，記得資料源是 SuggestionTab 的 `_item_cards` 勾選狀態，不是 plan 本身。

### 5. 既有測試的遷移風險

`test_safe_cleanup_dialog.py` 有 22,286 行（實際大小約 22KB），其中大量 assert 是對 `_tree` 的 QTreeWidgetItem 結構做驗證（`topLevelItem(0).child(0).text(1)` 之類）。重構後這些 assert 全部失效。建議：

- 不要直接刪舊測試，先加上 `@unittest.skip("v0.2 refactor")`，確保其他測試仍能通過
- 新的 SuggestionTab 測試從零開始寫，不繼承舊 assert 邏輯

### 6. 一個被我高估的設計：ProgressStepper

我在 §5 提了 9 點 ProgressStepper 動畫，ChatGPT 正確地把它 defer 了。回頭看，現有的 `QProgressBar` + stage name 文字已經夠用，stepper 只是加分項。唯一值得保留的是：把現有 `_scan_progress.setFormat(f"{name} ({index}/{total})")` 的 `index/total` 改成直接顯示階段名稱，讓使用者知道現在在掃什麼（例如「正在掃描：捷徑」），而不是看到 3/9 這種無意義的數字。這個不改結構，只改一行 format string，零成本。

## 8. 最終 Codex 指令書（由 ChatGPT 收斂後填入）

> 版本：`安全清除工作台_GUI重設計_codex指令書_v0.2`
> 目標：替換「清除建議」tab 的舊 QTreeWidget，建立卡片式、安全分層、證據可見的 UI。不得降低掃描覆蓋率，不得放寬 HKLM / blocked 安全邊界。

### 8.1 不可違反的邊界

1. 不改 `SafeCleanupDialog(context, parent)` 對外建構簽章。
2. 不改五個 layer 常數：`SAFE_LAYER / PROCESS_LAYER / REVIEW_LAYER / REGISTRY_LAYER / BLOCKED_LAYER`。
3. 不改 `apply_cleanup_plan(...)` 的安全語意：檔案一律先隔離，不真刪。
4. HKLM / Windows Installer / `BLOCKED_LAYER` 永遠只列出，不可勾，不可執行。
5. 不把低信心項目藏掉；只調整顯示層級、預設勾選與確認門檻。
6. v0.2 不做自繪危險滑塊，不做永久刪除，不做打字確認。

### 8.2 產品決策

#### 一鍵安全清除

保留：

```python
keep_layers = {SAFE_LAYER, REVIEW_LAYER}
```

但一鍵選取必須使用：

```python
is_default_cleanup_candidate(item)
```

也就是 review 只有在「高信心 + core 預設勾選 + 可執行」時才會進一鍵。一般 review 項目仍顯示，但預設不勾。

#### Review 層

- 顯示：預設顯示。
- 勾選：預設不勾，使用者可手動勾。
- 解鎖：不需要 toggle。
- 卡片上強制顯示 top 2 evidence。

#### Process / Registry 層

- 預設鎖住，不可勾。
- 使用者開啟「允許關閉程序」或「允許設定殘留清理」後，才可手動勾。
- apply 前若 selected ids 包含 process / registry，必須跳確認對話框。
- blocked 永遠不受 toggle 影響。
